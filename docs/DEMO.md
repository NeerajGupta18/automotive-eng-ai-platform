# 12-minute demo script and interview cheat-sheet

## Setup (once)
```bash
pip install -r requirements-dev.txt
AUTH_MODE=enforced uvicorn app.api.main:app --port 8000      # copy the admin token printed at first start
API_TOKEN=<admin token> python scripts/seed_demo.py           # HLDs, HARA item, TARA system, UDS spec, C code + tool logs
streamlit run ui/streamlit_app.py                             # sign in with the admin token
```
Create two engineers on the *Administration* page (e.g. `asha` = reviewer, `ravi` = engineer) and add them to project `bcm-demo`.

## The story: one change, traced through every discipline
1. **HLD (page 1)** - ask "Which component provides the vehicle speed?" (cited answer, refuses when evidence is weak). Show the 12 consistency findings and the review queue.
2. **HARA (page 2)** - triage hazards, assess an event (S/E/C need written rationale), see the ASIL computed by a rule table, derive a safety goal, draft FSR/TSR, fill the placeholders, allocate to `SWC_DoorLockCtrl`. Try approving your own work as `ravi`: refused (four-eyes). Approve as `asha`.
3. **TARA (page 3)** - analyze the BCM architecture, assess a threat (impact + attack potential -> computed risk), treat it, derive a cybersecurity goal, recommend controls (source, assumptions, alternatives). Show the coverage checklist and the "expert review required" note.
4. **UDS (page 4)** - extract the spec from the document, validate `27 01`, `27 02 <KEY>`, `22 01 00`, generate 118 tests, run them on the simulator, then run **all injected defects** and show every one is detected. Attach a test to the FSR as verification evidence.
5. **Code review (page 5)** - analyze, show a corroborated finding (own rule + cppcheck), open a fix and show "verified by re-analysis", upload `door_lock_ctrl_v2.c` as a new revision: findings become *fixed*, decisions carry over, the new `goto` appears. Findings in `DoorLockCtrl_Run10ms` carry the component's ASIL.
6. **Traceability (page 6)** - go back to HARA, **re-assess the approved event** (D -> QM). Open *Traceability*: the goal, requirements, the UDS test evidence and the code findings are on the **re-review worklist**, with the reason. This is the point of the whole platform.
7. **Administration (page 7)** - show the audit log, click *Verify audit chain*. Tamper with one audit row in SQLite and verify again: it names the broken entry.
8. **ADAS Virtual Validation (page 10, Phase 4)** - the first AEB campaign failed because AEB-009 has no scenario; propose boundary scenarios, approve them as a reviewer, simulate CCRb-12m-6 on the compiled C code, run a campaign with mutation testing (back-to-back 0 differences, 7/11 mutants killed) and release it as the second person. Then change a requirement and show the release is suspect on *Traceability*. Full script: [PHASE4_ADAS_VIRTUAL_VALIDATION.md](PHASE4_ADAS_VIRTUAL_VALIDATION.md).
9. **Release Readiness and Agent (page 11, Phase 5)** - NO-GO with owners and actions; confirm the waiting agent step that creates one ticket per blocker. **Integrations (page 12)**: import the OEM's ReqIF v2 and show that the customer's change flags AEB-005 and its released evidence; ask the agent for the impact. Full script: [PHASE5_AGENTIC_INTEGRATION.md](PHASE5_AGENTIC_INTEGRATION.md).
10. **Field Issues (page 13, Phase 6)** - six dealer complaints became three issues, each investigated automatically. FI-001: the phantom braking on AEB 2.4.0 is reproduced bit-exactly on the C code, traced to `confirm_cycles` 15 → 5, and the fix (15) passes every complaint and the regression. Confirm the hazard rating and the actions as `asha`; approve the field scenarios and run the verification as `ravi`; release and close as `asha`; show the 8D report. Contrast FI-002 (correct braking, no defect) and FI-003 (coding defect, rollback). Full script: [PHASE6_FIELD_ISSUE_INVESTIGATOR.md](PHASE6_FIELD_ISSUE_INVESTIGATOR.md).

## Questions you will be asked, and honest answers
| Question | Answer |
|---|---|
| Why not let the LLM decide ASIL / risk / expected UDS responses? | Those are deterministic engineering rules: they must be reproducible and auditable. The LLM is optional, used for Q&A and an opt-in code review, and every LLM finding must quote the exact source line or it is dropped. |
| Is the ASIL table / risk matrix / MISRA mapping correct? | They are explicit, versioned *example* rule sets. They must be checked against your licensed ISO 26262 / 21434 / MISRA copies before use. The libraries are synthetic. |
| Does the UDS simulator prove the tests are right? | No. It shares the oracle with the generator, so it proves consistency and defect-detection power, not that the specification or the oracle rules are correct. Verify the oracle against the OEM diagnostic spec. |
| How good is the code analyzer? | It is a heuristic analyzer without a compiler front end or data-flow engine: false positives and misses are expected. It complements a certified analyzer. The value is the lifecycle (fingerprints, triage carry-over, verified fixes, gate, SARIF). |
| Is it secure? | With `AUTH_MODE=enforced`: token authentication, per-project RBAC (deny-by-default, tested over every route), token-bound four-eyes, rate limits, hash-chained audit. No SSO/MFA, single process, no encryption at rest; TLS must come from a reverse proxy. The default dev mode has no access control. |
| What did you not verify? | A real LLM, sentence-transformers embeddings, the Docker build, CAPL in CANoe, SocketCAN. |
| Is the AEB simulation realistic? | It is a one-dimensional longitudinal model with a first-order brake and a simple radar model: good for regression and comparing control logic, not for sign-off. The value is the method: requirements as checks, SIL with back-to-back, mutation testing to measure the tests, gated release with change impact. Next steps would be a vehicle-dynamics simulator (OpenSCENARIO export is ready), HIL and the ECU toolchain. |
| Why both a Python model and C code? | The model is the readable specification; the C code is what ships. Back-to-back on identical inputs proves they behave the same, step by step, including the C code's own calibration constants. |
| Can the agent do something harmful? | It only has read tools and a few write tools (tickets, scenario proposals, a validation campaign; for field issues the hazard rating and the corrective actions). Every write waits for a person and then runs under that person's name, so four-eyes still applies; there is no tool that approves, releases or deletes, and asking for one is recorded as blocked. Tool results reach an LLM as untrusted data, and a test plants a prompt injection to prove it has no effect. |
| How does it fit into a company's tool landscape? | ReqIF for requirements from OEM tools (DOORS, Polarion), Jira for work items, signed webhooks from the audit log for CI/ALM/chat, a release gate for pipelines, an MCP server for AI assistants with the user's own permissions, Kubernetes for deployment. |
| Why is the field investigator "agentic" and not just a script? | It decides its own next steps from what it finds: which recordings reproduce, whether to retry the reconstruction with other assumptions, whether the code or the calibration is at fault, which parameter, whether to search a calibration or a rollback build, whether a hazard rating is needed at all. It uses the platform's tools (SIL, scenario library, requirements, ticketing), keeps a durable, audited trace and stops for people at the decisions they own. The engineering judgement inside each tool is deterministic and testable; that is deliberate for safety work. |
| How do you know it is right? | Every conclusion carries its evidence (bit-exact replay, the first differing cycle, the parameter that changes the reaction, the collision without AEB), the fix is verified against every complaint and the regression library, and a person confirms. On 27 labelled cases it found every root cause with no false defects, but those cases are synthetic; the first real test would be a batch of real recordings with known outcomes. |
| What would you do next? | PostgreSQL + multi-worker, OIDC gateway, a qualified static analyzer as an input, real libraries reviewed by domain owners, more UDS services (0x2F, 0x34-0x37), evaluation of retrieval quality on real HLDs. |
